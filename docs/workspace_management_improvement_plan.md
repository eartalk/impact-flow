# Impact Flow 工作空间与平台能力完善方案

## 1. 文档目标

本文档用于指导 Impact Flow 从“单一默认工作空间”升级为可创建、可切换、可治理的多工作空间平台，并同步规划成员协作、权限、安全审计、任务可靠性、业务资产映射和回归反馈闭环等后续能力。

本方案优先保证：

- 工作空间之间的数据严格隔离
- 现有服务管理、变更分析、AI 分析和自动化能力平滑迁移
- 不破坏当前用户和默认工作空间数据
- 分阶段交付，每个阶段均可独立验收

---

## 2. 当前现状

### 2.1 已具备的基础

当前系统已经存在以下多工作空间基础设施：

- `workspace` 工作空间表
- `workspace_member` 工作空间成员关系表
- `auth_session.workspace_id` 当前会话工作空间
- `OWNER / ADMIN / MEMBER / VIEWER` 四级角色
- 项目、AI 配置、通知配置和自动化策略的工作空间隔离
- `audit_log` 审计日志表
- 首次启动时创建默认工作空间及首位 OWNER

### 2.2 当前限制

当前产品和认证流程仍按照单工作空间运行：

- 登录固定进入默认工作空间
- 无工作空间列表接口
- 无创建、切换、修改、归档和恢复能力
- 一个账号即使属于多个工作空间，也无法在页面中切换
- 成员管理只能创建成员和修改角色
- 无成员移除、账号停用和密码重置
- 审计日志无查询接口和管理页面
- 缺少跨工作空间越权访问的自动化测试

因此，当前状态可以概括为：

> 数据模型初步支持多工作空间，但产品流程和认证流程仍是单工作空间模式。

---

## 3. 建设目标

目标工作流程如下：

```text
用户登录
  ↓
进入上次使用的工作空间
  ↓
查看自己有权限访问的工作空间
  ↓
创建或切换工作空间
  ↓
加载该空间下的服务、分析、配置与日志
  ↓
根据空间角色控制可执行操作
```

每个工作空间独立拥有：

- 服务和 Git 仓库配置
- 生产版本巡检记录
- 变更分析和 AI 分析记录
- AI Provider 配置
- 自动化执行策略
- 通知渠道及投递日志
- 成员和角色
- 审计日志
- 后续扩展的业务模块、页面和测试资产

---

## 4. 核心设计原则

### 4.1 工作空间上下文来源唯一

所有业务接口必须从服务端认证会话中获取当前 `workspaceId`，不得信任前端提交的工作空间 ID。

```text
HttpOnly Session Cookie
  ↓
auth_session.workspace_id
  ↓
AuthGuard 解析 AuthSession
  ↓
Repository 强制附加 workspace_id 条件
```

除系统级调度器外，任何业务 Repository 查询都必须显式携带 `workspaceId`。禁止业务流程调用无工作空间作用域的 `findAll()`、`findById()` 或日志查询。

系统级调度器确实需要读取全部工作空间数据时，必须先按 `workspaceId` 分组，再分别加载该空间的策略并进入后续业务流程。

现有代码需要在多工作空间功能上线前完成一次数据隔离审计，重点检查：

- 项目与关联仓库查询
- 跨仓库 Symbol 和 HTTP 调用链分析
- 分析任务恢复
- 定时巡检与自动化任务
- AI 配置、通知配置和日志查询
- 仅凭资源 ID 查询详情的接口

已知需要优先修复的路径是分析任务构建关联仓库时调用无作用域的项目列表。该查询必须改为只读取当前分析项目所属工作空间的仓库。

### 4.2 切换工作空间时轮换会话

切换工作空间不应只修改前端状态。服务端需要：

1. 验证用户是目标空间的有效成员。
2. 撤销或替换当前 Session。
3. 为目标工作空间签发新 Session。
4. 更新 HttpOnly Cookie。
5. 写入审计日志。

### 4.3 归档优先于物理删除

工作空间默认不提供物理删除，采用状态流转：

```text
ACTIVE → ARCHIVED → ACTIVE
```

归档后：

- 禁止创建新服务和新分析任务
- 停止定时巡检和自动化任务
- 保留历史分析和日志查询能力
- OWNER 可以恢复工作空间

### 4.4 所有敏感操作均需审计

成员、角色、密钥配置、通知配置、自动化策略和空间状态变化都需要写入 `audit_log`。

审计日志不得记录密码、Session Token、完整 API Key 或完整 Webhook。敏感配置只记录资源 ID、操作类型和脱敏后的变化摘要。

### 4.5 跨实体写入必须使用事务

以下操作必须由数据库事务保证原子性：

- 创建工作空间及其 OWNER、默认策略和通知配置
- 归档工作空间并处理待执行任务
- 恢复工作空间

任何一步失败都必须整体回滚，禁止产生无 OWNER、配置不完整或成员关系不一致的工作空间。

### 4.6 前端切换必须防止旧请求回写

切换工作空间时，旧空间已经发出的请求可能晚于新空间请求返回。前端必须使用以下至少一种机制阻止旧响应覆盖新状态：

- 使用 `AbortController` 取消旧空间请求
- 为每次空间切换生成 workspace generation 标记，写入状态前校验标记

同时需要停止旧轮询、清空页面状态、完成 Session 切换，再加载目标空间并重新启动轮询。

## 5. 第一阶段：工作空间创建与切换

### 5.1 后端接口

建议新增工作空间模块：

```text
apps/api/src/modules/workspaces/
  workspaces.controller.ts
  workspaces.service.ts
  workspaces.module.ts
  dto/
    create-workspace.dto.ts
    update-workspace.dto.ts
```

接口设计：

```http
GET    /api/workspaces
POST   /api/workspaces
POST   /api/workspaces/:id/switch
GET    /api/workspaces/current
PATCH  /api/workspaces/current
POST   /api/workspaces/current/archive
POST   /api/workspaces/:id/restore
```

#### 查询可访问工作空间

```http
GET /api/workspaces
```

响应示例：

```json
[
  {
    "id": "workspace-id",
    "name": "测试团队",
    "code": "qa-team",
    "description": "负责生产版本验收",
    "status": "ACTIVE",
    "role": "OWNER",
    "memberCount": 8,
    "projectCount": 12,
    "createdAt": "2026-09-21T10:00:00.000Z"
  }
]
```

#### 创建工作空间

```http
POST /api/workspaces
```

请求示例：

```json
{
  "name": "测试团队",
  "code": "qa-team",
  "description": "负责生产版本验收"
}
```

创建流程：

1. 验证用户级工作空间创建策略。
2. 验证名称和编码。
3. 检查编码全局唯一。
4. 开启数据库事务。
5. 创建工作空间并记录所有者。
6. 将创建者加入成员表并设置为 `OWNER`。
7. 初始化工作空间自动化策略。
8. 初始化通知配置。
9. 更新创建者最后使用的工作空间。
10. 写入 `WORKSPACE_CREATED` 审计记录。
11. 提交事务。
12. 自动把当前 Session 的 `workspace_id` 就地切换到新工作空间。

工作空间创建权限不复用当前空间的 `OWNER / ADMIN / MEMBER / VIEWER` 角色。任意已登录账号均可创建新工作空间，创建后自动成为该空间的 `OWNER`。

#### 切换工作空间

```http
POST /api/workspaces/:id/switch
```

服务端处理：

1. 校验工作空间为 `ACTIVE`。
2. 校验当前用户为该空间成员。
3. 撤销旧 Session。
4. 创建目标空间的新 Session。
5. 更新用户最后使用的工作空间。
6. 写入 `WORKSPACE_SWITCHED` 审计记录。
7. 返回新的 `AuthSession`。

### 5.2 前端交互

左侧账号区域升级为工作空间选择器：

```text
[ 测试团队 ▼ ]

✓ 测试团队
  研发团队
  预发布验证

────────────
+ 创建工作空间
  工作空间设置
```

创建工作空间弹窗字段：

- 工作空间名称，必填
- 工作空间编码，必填且唯一
- 描述，可选

切换工作空间时前端需要：

1. 停止项目刷新和分析轮询。
2. 调用工作空间切换接口。
3. 清空当前项目、分析详情、日志和配置状态。
4. 更新当前 `AuthSession`。
5. 加载目标空间数据。
6. 重新启动后台轮询。
7. 将主视图恢复到发布分析页。

所有 API 请求都应绑定当前 workspace generation。空间切换开始后，即使旧空间请求成功返回，也不得再更新任何页面状态。

如果用户在多个浏览器标签页中使用系统，任意标签页切换工作空间都会使旧 Session 失效。其他标签页收到 `401` 后应提示“工作空间已在其他页面切换”，并重新获取当前会话，而不是继续展示旧数据。

## 6. 数据库迁移设计

建议新增迁移：

```text
database/017_add_workspace_management.sql
```

### 6.1 workspace 表扩展

建议增加：

```sql
ALTER TABLE workspace
  ADD COLUMN description VARCHAR(500) NULL COMMENT '工作空间描述',
  ADD COLUMN owner_user_id CHAR(36) NULL COMMENT '当前所有者用户ID',
  ADD COLUMN created_by CHAR(36) NULL COMMENT '创建用户ID',
  ADD COLUMN updated_by CHAR(36) NULL COMMENT '最后修改用户ID',
  ADD COLUMN archived_at DATETIME(3) NULL COMMENT '归档时间';
```

`workspace.owner_user_id` 是工作空间唯一所有者的权威来源。`workspace_member.role = 'OWNER'` 用于权限查询和展示，两者必须在同一事务中维护。

建议增加外键和索引：

```sql
ALTER TABLE workspace
  ADD KEY idx_workspace_owner (owner_user_id),
  ADD CONSTRAINT fk_workspace_owner
    FOREIGN KEY (owner_user_id) REFERENCES user_account (id)
    ON DELETE RESTRICT;
```

保留现有状态字段：

```text
ACTIVE
ARCHIVED
```

### 6.2 user_account 表扩展

```sql
ALTER TABLE user_account
  ADD COLUMN last_workspace_id CHAR(36) NULL COMMENT '最后使用的工作空间ID';
```

建议将其设置为指向 `workspace.id` 的外键，并使用 `ON DELETE SET NULL`。由于工作空间默认采用归档而非删除，该外键主要用于保证数据完整性。

登录时的工作空间选择顺序：

1. `last_workspace_id` 对应的有效成员空间。
2. 用户拥有的第一个 ACTIVE 工作空间。
3. 用户加入时间最早的 ACTIVE 工作空间。
4. 无任何空间时拒绝登录，由管理员创建新的成员账号。

### 6.3 workspace_member 表扩展

建议增加：

```sql
ALTER TABLE workspace_member
  ADD COLUMN updated_at DATETIME(3) NOT NULL
    DEFAULT CURRENT_TIMESTAMP(3)
    ON UPDATE CURRENT_TIMESTAMP(3)
    COMMENT '成员关系更新时间';
```

### 6.4 数据迁移兼容

现有默认工作空间及数据保持不变：

- 现有项目继续属于默认工作空间。
- 现有首位所有者继续担任默认空间 OWNER。
- 现有 Session 可自然过期，无需批量失效。
- 为现有用户回填 `last_workspace_id`。
- 将默认工作空间现有 OWNER 回填到 `workspace.owner_user_id`。
- 对不存在 OWNER 或存在多个 OWNER 的异常数据，在迁移前终止并要求人工处理。

## 7. 第二阶段：成员与权限完善

### 7.1 成员生命周期

需要补充：

- 创建新账号并设置初始密码
- 移除成员
- 停用和恢复账号
- 重置密码
- 成员搜索和分页
- 查看最近登录时间
- 查看成员操作审计

成员由 OWNER 或 ADMIN 直接创建账号并加入当前工作空间，不提供已有账号加入或邀请链接流程。

### 7.2 权限矩阵

| 操作 | OWNER | ADMIN | MEMBER | VIEWER |
|---|---:|---:|---:|---:|
| 查看工作空间 | 是 | 是 | 是 | 是 |
| 修改工作空间信息 | 是 | 是 | 否 | 否 |
| 创建新工作空间 | 由系统级创建策略决定 | 由系统级创建策略决定 | 由系统级创建策略决定 | 由系统级创建策略决定 |
| 归档或恢复工作空间 | 是 | 否 | 否 | 否 |
| 管理成员 | 是 | 是 | 否 | 否 |
| 管理服务 | 是 | 是 | 是 | 否 |
| 发起变更分析 | 是 | 是 | 是 | 否 |
| 执行 AI 分析 | 是 | 是 | 是 | 否 |
| 管理 AI 和通知配置 | 是 | 是 | 否 | 否 |
| 查看分析和日志 | 是 | 是 | 是 | 是 |

### 7.3 OWNER 约束

- 每个工作空间必须且只能有一个 OWNER。
- OWNER 不能通过普通角色修改接口降级。
- OWNER 不能直接退出当前工作空间。
- OWNER 不能被移除或停用。
- 应用不提供所有权变更接口；`workspace.owner_user_id` 与 OWNER 成员关系在创建工作空间时确定。
- 移除成员时必须撤销该成员在当前工作空间下的全部 Session。

建议接口：

```http
DELETE /api/members/:userId
POST   /api/members/:userId/reset-password
PATCH  /api/members/:userId/status
```

## 9. 第四阶段：平台其他能力完善

### 9.1 P0：工作空间归档任务规则

归档工作空间时采用以下规则：

- 阻止创建新的巡检和回归分析任务
- 将尚未运行的 `READY` 任务标记为取消
- 已经 `RUNNING` 的回归分析允许完成持久化，但不得继续触发通知链路
- 已经发出的 AI 请求允许结束并记录结果，不再自动重试
- 撤销该工作空间下全部登录 Session
- 只有 OWNER 可以进入归档空间的只读管理页
- 恢复后保留原自动化配置，但不立即补跑历史巡检

归档操作和待执行任务状态变更需要在事务中完成。运行中任务在完成前必须再次检查工作空间状态。

### 9.2 P0：任务可靠性

当前分析任务主要依靠应用进程内队列执行。建议升级为独立 Worker：

- 工作空间级并发限制
- 全局并发限制
- 自动重试和指数退避
- 任务超时
- 多实例任务锁
- 任务取消
- 失败任务手动重试
- 死信任务处理
- 任务执行进度
- Git 和 AI 资源隔离

### 9.3 P0：回归反馈闭环

增加：

- 回归建议采纳和驳回
- 回归项勾选
- 执行人和执行时间
- 通过、失败、阻塞状态
- 实际缺陷关联
- 漏测原因回填
- AI 建议有效率
- 核心场景覆盖率
- 人工分析耗时变化

### 9.4 P1：业务资产映射

建立工作空间级业务资产模型：

## 12. 验收标准

多工作空间第一阶段至少满足：

- 同一账号可以拥有或加入多个工作空间
- 用户登录后进入上次使用的有效空间
- 用户可以创建新工作空间并自动成为 OWNER
- 用户可以在有权限的工作空间之间切换
- 切换后所有页面数据同步刷新
- 切换过程中旧请求不会覆盖目标空间数据
- 项目、分析、AI 配置、通知和日志严格隔离
- 跨仓库调用链分析只能读取同一工作空间项目
- 无法通过伪造请求参数访问其他工作空间资源
- 工作空间切换会轮换认证 Session
- 归档空间不再执行巡检和自动分析
- 归档和恢复具备明确的任务状态处理规则
- 工作空间创建具备事务保护
- 所有敏感操作均有审计记录
- 核心接口具备单元和集成测试
- 创建、切换和隔离流程具备 E2E 测试

## 13. 推荐优先级

| 优先级 | 能力 | 原因 |
|---|---|---|
| P0 | 数据隔离审计与修复 | 防止跨工作空间数据泄漏 |
| P0 | 工作空间创建与切换 | 当前多空间模型无法实际使用 |
| P0 | Session 上下文切换与数据隔离测试 | 决定多租户安全边界 |
| P0 | 成员创建、移除和账号状态治理 | 完善成员生命周期 |
| P0 | 任务队列可靠性 | 保证自动化任务稳定执行 |
| P0 | 回归反馈闭环 | 验证平台是否真正有效 |
| P1 | 工作空间设置与审计页面 | 提升治理和可追溯性 |
| P1 | 业务资产映射 | 提高回归建议的业务准确性 |
| P1 | 前端状态和样式继续拆分 | 提高可维护性和测试能力 |
| P1 | 多渠道通知 | 提升故障和待办触达能力 |

## 14. 最终建议

下一步优先实施“迭代 0：数据隔离审计”，随后实施“迭代 1：多工作空间基础”。

现有 `workspace_id` 数据隔离机制可以继续复用，但必须先修复无作用域的项目和关联仓库查询。之后再补齐工作空间生命周期、登录空间选择、Session 切换、创建事务和前端请求竞争保护。

第一阶段完成后，Impact Flow 将从单团队内部工具升级为可以承载多个独立团队的正式平台，为后续权限治理、业务资产和回归反馈闭环提供稳定基础。
